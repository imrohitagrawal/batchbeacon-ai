# Unconfirmed-check operator procedure

Responsible operator: the BatchBeacon project owner. Under U34 the owner selected
`rohit@stackclimb.com` as the public support mailbox. The optional typed
`BATCHBEACON_SUPPORT_EMAIL` deployment setting supplies the public contact; missing
configuration keeps the explicit unavailable message, and malformed values stop
startup. A mail link opens the visitor's email application with a generic subject;
it does not send anything or attach case data. The owner authorized one verification email and confirmed receipt with an inbox
screenshot. This verifies that test handoff, not ongoing delivery or case resolution. The private
monitoring destination is not reused.

The interface must continue to say that no notification was sent and no response
period is promised. The copyable case reference is an identifier, not a credential.
It must not contain cookies, tokens, provider bodies or private logs. Saved labels
and the exact official notice remain available only while owned access is valid.

Operator procedure for the approved mailbox:

1. Ask for the displayed case reference, observed message and whether access is
   still active. Do not request authentication cookies or tokens. Explain the
   non-production sample scope; do not ask the visitor to publish private logs.
2. Inspect owned incident/run/completion records and the original attempt’s bound
   request, response, usage, configuration, grant and rate evidence privately.
   Distinguish incomplete execution, unsupported usage, accepted completion and
   already-settled failure. A timeout or HTTP 200 alone is not settlement proof.
3. Preserve all reservations and failed evidence. Do not use new keys, a fresh
   workspace, longer deadlines or an assumed zero charge to erase unknown liability.
   No further paid AI calls are authorized by this procedure.
4. If existing evidence permits a supported recovery, prepare its precise record
   preimages/postimages, concurrency/idempotency guards and original-liability
   compatibility proof. Obtain independent technical review and apply only within
   a separately admitted operational scope. Missing proof remains unresolved.
5. Tell the visitor to use Recheck saved status. This GET observes completion and
   availability; it neither calls AI nor performs settlement. Expired access
   cannot be restored through the UI, and a new workspace does not inherit cases.
6. Verify delivery and the user-visible readback before claiming that this route
   works. Record observed receipt and outcome separately from configuration.

F8 analysis verified two different causes: a newer complete response with cached
prompt usage rejected by the old parser, and an older attempt without a complete
response. The corrected parser validates cache subsets and conservatively values
the full prompt at its original bound rate; this is not an invoice or cache-discount
claim. Offline and emulator evidence is recorded in M9. Both liabilities remain
held; no failed run becomes a successful extraction through this correction.

A prepared private proposal covers only the newer retained receipt, exact
preimages/postimages and idempotent transactional reconciliation. It still requires
explicit owner authority, current ledger/configuration checks and a verified
cache-aware rollback. Settlement may reopen shared public admission; it does not
reserve capacity for validation. No new model/countTokens call, retry, email or
settlement is authorized by this runbook. Fresh model/product acceptance and actual
human/assistive-technology observation remain separate gates.
